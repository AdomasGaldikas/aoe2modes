## P1 — Blocking: the reference layer is not what it claims to be

### [~] B1. `generated/` was hand-edited but still claims to be regenerable

`generated/triggers/__init__.py` cannot be output of the current decompiler:
`src/aoe2modes/lib/decompile.py:638-655` emits the `VARIABLES` block, its two `#:`
comment lines, the `for variable_id, name in VARIABLES:` loop, and the docstring
*"Declare the variables, recreate every trigger, restore display order"* — all
**unconditionally**, even for an empty variable list. The committed file has none of
them and a different docstring. `part_008` was also dropped from `PARTS` by hand and
`DISPLAY_ORDER` trimmed 2029 → 1989 entries.

The file header still says *"Regenerating overwrites this file"*. Today, regenerating
would silently discard the hand-made state and produce a materially different scenario.

**Decide first:** is `generated/` still a decompile, or is it now hand-maintained source?

- If **hand-maintained**: replace the "Generated by `aoe2modes decompile`" header with a
  header saying so, and stop listing `decompile --mode evolution_alpha` as a valid step
  for this mode in `AGENTS.md` / `CLAUDE.md` / `docs/tooling.md`.
- If it should stay **regenerable**: re-decompile from a reference that actually
  reproduces it, and move the hand deletions into `build.py` as post-generation passes.

## P2 — Correctness

### [ ] C1. Anti-trebuchet kill zones are not mirrored

`build.py:1231` `anti_treb_bounds` is **1/8** mirror-consistent. `wall_cleanup_bounds`
in the same function (`build.py:1264`) is **8/8** — so the convention was known and
applied correctly ten lines away. Castles verified in the built file at 19 / 125,
mirroring under `144 − p`:

```
P1 zone=(39,19,66,25)    castles covered 4/4
P2 zone=(75,19,102,26)   castles covered 4/4
P3 zone=(18,38,25,64)    castles covered 4/4
P5 zone=(18,74,24,101)   castles covered 4/4
P4 zone=(114,38,123,65)  castles covered 0/4   <-- zone stops at 123, castles at 125
P6 zone=(114,74,123,101) castles covered 0/4
P7 zone=(39,116,66,123)  castles covered 0/4
P8 zone=(74,116,102,123) castles covered 0/4
```

Effect: a trebuchet parked on the castle line is removed in P1/P2/P3/P5's base and
survives in P4/P6/P7/P8's — a live counterexample to ASC-003 ("eight equal mirrored
fortified territories").

- [ ] Regenerate all eight zones from one source rect through `v2_map`'s transform
      instead of hand-listing them, the way `wall_cleanup_bounds` already works out.
- [ ] Replace the tautological test (see T1) with a symmetry + castle-coverage assertion.

### [ ] C2. Civ array size is a magic `60`, not derived from the civ table

`CIV_SPAWN_RULES` and `CIV_BUILDER_RULES` both cover exactly 1–59, no gaps, no mismatch —
that part is sound. But `xsArrayCreateInt(60, …)` is hardcoded in five places
(`build.py:1802-1806`).

- [ ] Derive the array size from `len(CIV_SPAWN_RULES) + 1` so the two cannot drift.
- [ ] Give civ ids outside the table a visible failure: today `civilization >=
      xsArrayGetSize(...)` returns early, so a player on a future DLC civ gets **no army,
      no builder pairs, and no message** — a silently dead game. A chat warning or a
      default unit is better than silence.
- [ ] Note that adding civ 60 to the Python table today writes out of bounds at runtime;
      `xs-check` cannot catch it.

## P3 — Architecture

### [ ] A1. Variable ids come from four allocators with no registry

Ids 0–96, no gaps, and all six bases currently agree with the XS (checked at every
access site). But two ranges use bare literals instead of named constants:

- `pending_builders` base 0 — `int(player) - 1` in Python, `scenarioPlayer - 1` in XS.
- **K/D/R base `8`** — a raw literal duplicated across languages: `build.py:4151`
  (`8 + ((player_number - 1) * 3)`) and `build.py:1776`
  (`int variableBase = 8 + ((scenarioPlayer - 1) * 3);`). Change one, nothing flags the other.

- [ ] Add `PENDING_BUILDER_VARIABLE_BASE` and `COMBAT_ROW_VARIABLE_BASE`, and interpolate
      both into the XS the way `COLOR_WORLD_VARIABLE_BASE` already is.
- [ ] Add one assertion after all allocation that the id set is exactly `range(0, N)` with
      no duplicates, so a future collision fails the build instead of the lobby.

### [ ] A2. The documented Python↔XS bridge is bypassed

`CLAUDE.md` describes `lib/variables.SHARED` mirrored as `const int VAR_*` in
`xs/lib/util.xs`. This mode uses neither: `mode.toml` declares `[xs] include = []` and
`scripts = []` while the build embeds 606 lines generated inline by
`_render_color_spawn_xs`.

- [ ] Either adopt the shared bridge, or document that this mode deliberately generates
      its XS and that `[xs]` in `mode.toml` does not describe it.

### [ ] A3. `free_costs.py` is dead code

128 lines; the module is never imported. Costs are actually zeroed by the XS `main()`
loop, and `tests/test_evolution_alpha.py:1472` asserts the trigger contains **no**
`CHANGE_OBJECT_COST` effects. `docs/ascendants-development.md:18` lists it as one of the
three files forming the patch layer, so anyone tuning that list will change nothing while
believing they did.

- [ ] Delete it, or wire it up if the id list is meant to drive the feature.
- [ ] Remove it from `docs/ascendants-development.md:18` either way.
